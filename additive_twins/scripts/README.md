# Finding hand-written `to_additive` twins

Two tools, one pattern:

* `scan_to_additive.lean` — an **environment-level scanner**: it asks `to_additive` itself
  which declarations it *would* generate, and reports the ones that are already there,
  written out by hand.
* `to_additive_twins.py` — the **decider**: for every candidate it really tags the
  partner, really deletes the hand-written twin, rebuilds the file and checks that the old
  statement survives; it also emits the diff. It can generate candidates on its own from
  the source text (`find`/`verify PATH...`) or read them from the Lean scan (`--scan`).

`deletion_scout.py scan-twins` calls into the Python module for its own twin heuristic.

## The pattern

```lean
@[to_additive]                              -- missing
theorem prod_range_reflect (f : ℕ → M) (n : ℕ) : ... := by ...

theorem sum_range_reflect {δ : Type*} [AddCommMonoid δ] (f : ℕ → δ) (n : ℕ) :   -- redundant
    (∑ j ∈ range n, f (n - 1 - j)) = ∑ j ∈ range n, f j :=
  @prod_range_reflect (Multiplicative δ) _ f n
```

The additive lemma is written out by hand; tagging the partner generates exactly that
declaration, so the hand-written one is pure redundancy — the fix removes lines and
changes no API. The additive twin does not have to be proved through `Multiplicative`:
the same redundancy occurs whenever the twin's statement is the `to_additive` translation
of its partner's, whatever its proof looks like.

## Usage

```
lake env lean scripts/scan_to_additive.lean > scan.txt          # whole environment (~7 min)

scripts/to_additive_twins.py find   PATH... [--scan scan.txt]   # list candidates (seconds)
scripts/to_additive_twins.py verify PATH... [--scan scan.txt] [--twin NAME] [--patch out.patch]
```

Without `--scan`, `PATH...` is any mix of `.lean` files and directories to scan textually.
With `--scan`, `PATH...` are the roots under which the modules named in the scan output are
looked up (e.g. `.lake/packages/mathlib .lake/packages/batteries`).

As a library: `find_twins(paths)` and `twins_from_scan(text, roots)` produce `Twin`
records, `verify_twin(twin)` returns `(ok, message, patched_source)`.

## How candidates are found

**Source text (`find PATH...`).** A declaration whose whole proof is a call to a
same-file partner through `Multiplicative`/`Additive`. Fast and self-contained, but it
only sees that one syntactic shape.

**Environment (`scan_to_additive.lean`).** For every theorem `src` that is not already
tagged and was not itself generated by `to_additive`, the scanner computes

* the name `to_additive` would give it — `GuessName.guessName`, the very function the
  attribute uses;
* the statement it would give it — `applyReplacementForall`, the expression translation
  `@[to_additive]` applies to the type of a tagged declaration.

If a hand-written declaration in the *same module* has that statement (compared with
`isDefEq` under `withReducible`, and with universe parameters turned into metavariables),
the pair is reported:

```
CANDIDATE <module> <src> <tgt> auto        -- named exactly as `to_additive` would name it
CANDIDATE <module> <src> <tgt> renamed     -- statement matches, name does not: needs `@[to_additive tgt]`
```

Two deliberate restrictions keep the list usable: only theorems (for a `def` an agreeing
type says almost nothing — `Polynomial.instMul` and `Polynomial.instAdd` have
translated-equal types and nothing to do with each other), and `withReducible` rather than
default transparency (which would equate unrelated closed statements such as `0! = 1` and
`1! = 1`).

## What "verify" means here

Neither scanner is trusted; both only *propose*. For each candidate the Python module

1. compiles the file unchanged and records the pretty-printed type of the twin
   (`#check @Ns.sum_foo`);
2. rewrites the file — `@[to_additive]` onto the partner (merged into an existing
   attribute list, since Lean allows only one `@[...]` per declaration, and moved onto its
   own line if the merge would exceed the 100-column limit; the explicit target name is
   added only if the naming heuristic needs it) and the twin deleted, docstring and
   attributes included;
3. compiles again, requiring that the file still builds and that the *old* statement still
   typechecks against the new declaration, via an appended
   `example : <old type> := @Ns.sum_foo`. If that statement cannot be written down (a
   universe the pretty printer does not bind, say), it falls back to requiring the printed
   statement of the generated declaration to be character-for-character the old one;
4. restores the file — always, including on failure — and reports PASS/FAIL.

Several twins in one file are chained in source order and retried while anything succeeds
(tagging `prod_Ico_reflect` is what makes `prod_range_reflect`, whose proof uses it,
translatable), and `--patch` writes the accumulated unified diff with paths relative to the
innermost lake package, ready for `git apply` in that repo.

A twin is only ever deleted as a whole declaration: its span is its docstring and
attribute list (both may run over several lines) plus the indented body below its head,
and the deletion is refused outright if anything in that span starts in column 0.

## Results on the Mathlib pinned by this project (`v4.28.0`)

The environment scan reports 334 candidates in ~7 min, of which 31 are hand-written
`theorem`/`lemma`s that the Python side can locate in the source (the rest are
compiler-generated declarations such as `mk.injEq`, `ext_iff` or `brecOn`, which have no
source text to delete). `verify` settles those 31 in ~25 min: **16 PASS**, in seven files:

| file | twins that `@[to_additive]` regenerates |
| --- | --- |
| `Mathlib/Algebra/BigOperators/Intervals.lean` | `Finset.sum_Ico_reflect`, `Finset.sum_range_reflect` |
| `Mathlib/Algebra/BigOperators/NatAntidiagonal.lean` | `Finset.Nat.sum_antidiagonal_succ`, `…_succ'` |
| `Mathlib/Algebra/BigOperators/Expect.lean` | `Finset.expect_neg_index` |
| `Mathlib/Algebra/Group/Translate.lean` | `translate_sum_right` |
| `Mathlib/Algebra/Group/Action/End.lean` | `AddAction.toPerm_zero` |
| `Mathlib/RingTheory/FiniteType.lean` | `AddMonoidAlgebra.fg_of_finiteType`, `AddMonoidAlgebra.finiteType_iff_group_fg` |
| `Mathlib/Tactic/LinearCombination'.lean` | `pf_add_c`, `c_add_pf`, `add_pf`, `pf_sub_c`, `c_sub_pf`, `sub_pf`, `neg_pf` |

The first four were the earlier contribution (`contribution/to_additive-reflect.patch`);
the other twelve are new, and only the environment scan finds them — their proofs are
ordinary tactic scripts or term proofs, not transports through `Multiplicative`. The
generated diff is `contribution/to_additive-env-generated.patch` (−45/+17 lines, applies
with `git apply`), the full log is `contribution/verify-env.txt`, and the tool again
reports that the section variable `N` in `NatAntidiagonal.lean` becomes unused.

The 15 rejections are all decided by the compiler, and fall into three groups: the module
does not import `to_additive` at all (`Mathlib/Data/Set/Insert.lean`, and three twins in
`Batteries`, which cannot depend on Mathlib); `to_additive` refuses to build the
translated proof (`AddSubmonoid.mem_closure_singleton`, the `GrpCat` lemmas, …); or the
file stops compiling for a reason of its own — deleting `AddGroup.fg_def` makes a `⊤.FG`
dot-notation elsewhere in the file ambiguous, and the two `ArithmeticFunction` twins are
the *multiplicative* ones, obtained via `Additive`, a direction `to_additive` does not
generate.

## Known limitations

* Only the local case is reported: if the partner lives in another module, deleting the
  twin is not a self-contained diff, so such matches are dropped.
* Follow-on cleanups are reported, not performed — e.g. section `variable` binders that
  become unused after a deletion (`note:` lines) still have to be removed by hand.
* Candidates are decided on their own file. Downstream call sites keep working because
  the generated declaration has the same name and statement; for the 16 accepted here that
  was also checked by rebuilding the seven patched modules with their dependency closures
  (`contribution/patched-build.txt`) and every other Mathlib file mentioning one of the
  deleted names (`contribution/downstream-check.txt`).

## Independent Lean check

`RequestProject/MathlibContributionEnv.lean` re-checks ten of the accepted twins without
the scripts: it copies each multiplicative lemma verbatim, tags it `@[to_additive]`, and
asserts `@Generated = @Mathlib.Name := rfl`. Build it with
`lake build RequestProject.MathlibContributionEnv`.
